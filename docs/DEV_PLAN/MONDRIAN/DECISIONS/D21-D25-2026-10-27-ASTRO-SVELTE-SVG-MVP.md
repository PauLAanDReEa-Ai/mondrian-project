## What was conflated, and what wins

Three different products were being specified as one. They are not:

| Concept | Correct implementation | MVP? |
| --- | --- | --- |
| **Pre-saved pattern / work buttons** | Static JSON + SVG generated by Python at **build time**, bundled into the Astro PWA | **Yes** |
| **Custom pattern calculation** | FastAPI `POST /api/v1/patterns/calculate` with a JSON body (never query-string for nested geometry) | **No** — Phase 2 |
| **Interactive resize / variation** | Entirely client-side (Svelte island + SVG). No backend round trip | **Yes** — frame only, not internal edges |

Rule for every button: *does this need Python’s mathematical authority right
now, or can the browser apply an already-computed model?* If Python already
computed it at build, the button loads a file.

GitHub Pages is a pedagogical constraint, not a preference: **the public
MVP has no runtime Python.**

## D-23 Computation topology (clarifies D-09)

```text
Astro PWA  (GitHub Pages)
  ├── static pattern catalog   ← Python at build
  └── Svelte editor island     ← client geometry + variations that are
                                 mirrors/rotates/contrast (cheap)

FastAPI service  (studio LAN, M5)
  ├── GET  /works, /works/{id}, /works/{id}/preview
  ├── POST /analyze
  └── (Phase 2, last features) POST /api/v1/patterns/calculate
                POST /api/v1/patterns/generate   ← seeds: complexity, density, colorimetry
                POST /api/v1/exports/pdf
                POST /api/v1/designs
```


They may later share a domain (`/api/v1/` reverse-proxied). They remain
**separate deployable services.** Astro must not execute Python.

| Button / action | Backend? | Why |
| --- | --- | --- |
| Apply a measured work / preset | **No** | Load `/patterns/<id>.json` |
| Apply a predefined variation | **No** | Load a build-time artefact, or apply a pure matrix function |
| Drag frame corner | **No** | Client geometry; liquid-fill (D-30) |
| Hue / contrast / line weight | **No** | Client state + CSS custom properties |
| Generate a custom recursive pattern | **Yes** | Phase 2, Python authority |
| Fit a complex pattern exactly to a print size with bleed | **Yes** | Phase 2 |
| Server PDF job | **Yes** | Phase 2; MVP print is client `window.print()` + SVG |
| Save/share to a server | **Yes** | Not MVP; URL + local draft instead |

Build-time emission (M2 prebuild, Analyzer lane):

```text
python -m mondrian_work_schema.catalog
→ services/web/public/patterns/<workId>.json
→ services/web/public/patterns/<workId>.svg
→ services/web/public/patterns/<workId>--<variation>.json
→ services/web/public/patterns/<workId>--<variation>.svg
```

Measured `work.yml` remains the immutable source (D-12, D-16). Catalog
files are derived and gitignored-or-generated-in-CI; they are never hand
edited. Golden-ratio / rule-of-thirds **grids** are not a substitute for
measured Mondrian works; they may appear later as a labelled
`mathematical-study` collection, not as fake paintings.

## D-24 MVP interaction cut (amends D-16 game clauses)

Addendum B is now the MVP interaction law. It **supersedes** internal
divider/junction dragging for the minimum viable product.

**In MVP:**

1. Print-size (or digital surface) selection.
2. One overall containing frame, maximised at the work’s native ratio
   inside the printable area.
3. Frame resize by **corner handles** with **free aspect**; pattern
   **liquid-fills** the frame (D-30 supersedes preserve-ratio here).
4. Application of predefined measured works (the catalog).
5. Predefined deterministic variations (below).
6. Hue rotation, explicit palette inversion, line-weight scale (existing
   pedagogical claims — they do not require node dragging).
7. Undo / reset / compare, URL recipe, local draft, client export, print.

**Not MVP (Phase 2 interactive-editing):**

- Dragging internal dividers, junction nodes, or internal edges.
- Splitting or merging areas interactively.
- Edge-midpoint handles on the containing frame (corners are enough).
- Fraction-rewriting `refit` solver (not the same as liquid-fill).
- User-defined / recursive pattern generation.
- Runtime FastAPI from the public or kiosk app.

**Hierarchy** (amended by D-30)

```text
Print / digital canvas     (fixed SurfaceSpec)
└── Overall containing frame   (free-aspect corners, clamped)
    └── Predefined work / variation
        └── Fit: liquid-fill (fractions → full frame)
```

**Required MVP variations** (each preserves `Σ area(rects) = area(pattern
bbox)`, no gaps, no overlaps, minimum-area constraints, print canvas
unchanged):

| Variation | Effect | Where computed |
| --- | --- | --- |
| Original | Restore the measured work | catalog |
| Mirror horizontal / vertical | Reflect partition | JS + Python (must agree) |
| Rotate 180° | Both mirrors | JS + Python |
| Invert visual rank | Reverse visual-weight order | Python catalog artefact |
| Complement weights | Dominant ↔ subordinate areas | Python catalog artefact |
| Reciprocal weights | Strongly emphasise formerly light areas | Python catalog artefact |
| Equalize | Move target weights toward equal distribution | Python catalog artefact |
| Invert contrast | Geometry unchanged; colour/value/texture emphasis flips | JS + Python (HSL involution already specified) |
| Pattern variant = another catalog work | Alternative measured composition | catalog |

Styling-only inversions do not move edges. Weight operations that would
move edges are **precomputed**, not solved in the browser.

**No invented proportions.** Invert-rank / complement / reciprocal /
equalize must be closed-form functions of the measured visible-cell area
shares, written in `packages/works/schema/README.md` and implemented
identically in Python `vary.py`. If a function cannot be stated without
an aesthetic guess, it does not ship — drop it from MVP rather than
invent a partition.

**Frame handles:** corner drag = preserve aspect; edge drag = deferred.
The frame stays inside the printable area and respects a minimum size.

## D-25 Cohort git surfaces (amends rationale §8 ownership, not D-01)

D-01 stands: **one public cohort monorepo**, students as collaborators,
protected `main`, authorship via `packages/works/<slug>/`,
`docs/plans/<handle>/`, CODEOWNERS, history. Do not split into per-student
repos unless the department vetoes D-01.

The thread’s “backend vs frontend” split is mapped onto **path-owned
lanes**, so Git coordination does not fight the product:

| Seat / lane | Owns (CODEOWNERS) | Must not own |
| --- | --- | --- |
| **1 Analyzer** | `packages/analyzer/`, `packages/works/python/`, catalog generator | Svelte; Astro story pages |
| **2 API** | `services/api/` (M5; Phase-2 generate last) | Pages runtime API imports |
| **Geometry contract** (dual: 1–2 ∩ 6–7) | `packages/works/schema/`, `packages/matrix/` | Anything that imports `svelte` |
| **3–5 Shell & Story** | Astro pages except create/kiosk; About/gallery/method/declaration | Editor island internals |
| **6 Editor** | `packages/editor/`; create/kiosk pages | Schema changes without a matrix PR |
| **7 Export + Design** | `packages/tokens/` barrel; export/print/PWA/QR recipe; visual QA | Unilateral geometry edits |

Full task IDs: [`../TEAM-ASSIGNMENTS.md`](../TEAM-ASSIGNMENTS.md). Export/QR/generate: **D-26**.

**Merge bottleneck.** `packages/matrix` and `work.schema.json` are the
only paths every lane depends on. Rules:

1. PRs that change the schema, a derivation, or fixtures land **alone**
   (already a cascade hard constraint). Dual-lane human approval
   (Analyzer **and** Editor).
2. Do not mix a Svelte UI change and a schema change in one PR.
3. Short-lived `lane/<handle>-issue-<n>-<slug>` branches from current
   `main` (D-19). No stacked Editor→Shell→Analyzer branches.
4. Catalog JSON/SVG is generated in CI / `pnpm build`; do not commit
   derived blobs unless a phase explicitly snapshots a golden file.
5. FastAPI lives in `services/api/` so Pages deploys cannot accidentally
   import it.

This is the same TTOD hygiene (student-owned conflicts, no open-PR
rename, `Ready for re-review`, comments-only Ollama) with one extra
sentence: **Svelte stops at `packages/editor`; Python stops at catalog
generation plus LAN API.**

## Phase 2 (named so it cannot leak into M1–M7)

- Internal node/edge dragging (whole-figure proportional, not only
  adjacent cells — that research remains valid, just not MVP).
- Refit-to-frame solver.
- FastAPI `POST /patterns/calculate` and server-side PDF.
- Accounts, cloud save, public visitor gallery.
- XYFlow or any node-graph library.
- **Make your own Mondrian (last):** FastAPI `POST /api/v1/patterns/generate`
  with seeds complexity / density / colorimetry / RNG — output validates
  `work.schema.json`, labelled algorithmic study (see **D-26**). Not an
  unlabeled fake gallery.
- Full HTML+SVG inside a QR code (rejected; D-26 ships recipe-URL QR +
  downloadable HTML instead).
